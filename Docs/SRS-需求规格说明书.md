# 游戏需求规格说明书（SRS）

**文档版本：** V0.1  
**项目状态：** 需求设计阶段  
**项目类型：** 多人在线合作 PvE 地牢射击游戏  
**参考类型：** 《元气骑士》  
**目标平台：** Android
**最大联机人数：** 4 人

---

## 1. 项目概述

### 1.1 项目背景

本项目计划开发一款基于客户端-服务器架构的 2D 俯视角多人在线合作地牢射击游戏。

玩家可以创建或加入游戏房间，与其他玩家组成队伍，共同探索由多个预制房间组成的地牢。在探索过程中，玩家需要击败不同类型的怪物、躲避攻击、获取道具，并最终挑战 Boss 完成地牢探索。

项目以多人实时协作作为核心玩法，同时重点研究实时网络游戏中的服务端权威模拟、客户端预测、状态校正和实体插值等技术。

### 1.2 项目目标

本项目包含两个主要目标：

**游戏产品目标**

实现一款具有完整游戏流程的多人合作地牢射击游戏，包括玩家管理、房间管理、地牢探索、实时战斗、道具交互和游戏结算。

**技术研究目标**

构建一套基于 Go 游戏服务器和 Unity 客户端的实时网络通信与同步架构，实现：

1. 基于 Protobuf 的跨语言通信协议。
2. 基于 KCP/UDP 的网络传输。
3. 基于固定 Tick 的服务端权威模拟。
4. 基于客户端预测的本地玩家移动。
5. 基于状态校正的预测同步机制。
6. 基于快照插值的远端实体平滑表现。
7. 网络延迟、丢包环境下的同步效果测试。

### 1.3 技术选型

| 模块 | 技术 |
| --- | --- |
| 游戏客户端 | Unity + C# |
| 游戏服务器 | Go |
| 通信协议 | Protocol Buffers |
| 可靠传输 | KCP |
| 实时传输 | UDP（后续评估拆分） |
| 业务接口 | HTTP |
| 数据存储 | SQLite |
| 部署环境 | Docker |

服务器采用完整服务端权威模拟架构。所有影响游戏最终结果的逻辑均由服务端计算，客户端负责输入采集、局部预测和画面表现。

## 2. 游戏核心玩法

### 2.1 游戏类型

2D 俯视角、多人合作、房间制地牢射击游戏。

玩家通过键盘和鼠标控制角色移动、瞄准和攻击，与队友共同完成地牢探索。

### 2.2 核心游戏流程

整体游戏流程如下：

1. 玩家启动客户端并登录。
2. 进入游戏大厅。
3. 创建房间或加入已有房间。
4. 等待其他玩家加入并准备。
5. 房主启动游戏，所有玩家进入地牢。
6. 玩家在房间中击败怪物。
7. 清除当前房间的全部敌人后，出口解锁。
8. 所有存活玩家进入出口，切换到下一个房间。
9. 完成若干普通房间后进入 Boss 房间。
10. 击败 Boss，完成地牢探索。
11. 服务端计算最终成绩并保存对局记录。

如果所有玩家均被击败，则本局游戏失败。

### 2.3 玩家操作

| 操作 | 默认输入 | 功能 |
| --- | --- | --- |
| 向上移动 | W | 角色向上移动 |
| 向下移动 | S | 角色向下移动 |
| 向左移动 | A | 角色向左移动 |
| 向右移动 | D | 角色向右移动 |
| 瞄准 | 鼠标位置 | 确定攻击方向 |
| 普通攻击 | 鼠标左键 | 发射武器 |
| 主动技能 | Space | 使用技能（后续实现） |
| 交互 | E | 拾取或触发交互 |

角色支持八方向移动，斜向移动需要进行归一化处理，避免移动速度异常。

### 2.4 摄像机

采用 2D 俯视角正交摄像机。

摄像机跟随本地玩家角色移动，并受到当前房间边界限制。

每个客户端独立控制自己的摄像机，不同步摄像机位置。

当玩家靠近房间边缘时，摄像机不应显示房间以外的无效区域。

## 3. 游戏系统功能需求

### 3.1 用户系统

实现基础用户管理功能。

- 用户注册或创建游戏账号。
- 用户登录。
- 用户基本信息查询。
- 用户游戏统计数据查询。

初期不实现第三方登录、好友系统和复杂账号安全体系。

### 3.2 大厅与房间系统

玩家登录后进入大厅。

主要功能：

- 创建游戏房间。
- 通过房间号加入房间。
- 显示房间内玩家列表。
- 显示玩家准备状态。
- 玩家准备与取消准备。
- 房主启动游戏。
- 玩家退出房间。

房间规则：

- 一个游戏房间最多容纳 4 名玩家。
- 至少需要 2 名玩家才能启动正式多人对局。
- 房主拥有开始游戏的权限。
- 游戏开始后禁止新玩家加入。
- 房主退出时，由服务端重新指定房主或结束房间。

### 3.3 地牢探索系统

地牢由多个预先设计的房间组成。

采用固定顺序串联的地图结构，不在 MVP 阶段实现复杂的随机地图生成。

房间类型包括：

- 普通战斗房间。
- Boss 战斗房间。

每个房间具有独立的地图、出生点、怪物生成配置和出口。

房间内所有敌人被击败后，出口解锁。

玩家进入出口区域后，服务端检查队伍成员状态。当所有存活且仍在本局游戏中的玩家进入出口区域后，触发房间切换。

### 3.4 玩家角色系统

第一版仅实现一种基础角色。

角色属性包括：

- 玩家 ID。
- 当前位置。
- 当前速度。
- 最大生命值。
- 当前生命值。
- 朝向。
- 当前角色状态。
- 当前武器。
- 攻击冷却时间。

角色状态：

- Idle：待机。
- Moving：移动。
- Attacking：攻击。
- Damaged：受伤。
- Dead：被击败。

玩家受到攻击时减少生命值。

生命值归零后进入被击败状态，不能继续移动和攻击。

如果所有玩家均被击败，本局游戏失败。

MVP 暂不实现队友复活机制。

### 3.5 武器与攻击系统

第一版实现基础远程射击武器。

武器包含：

- 攻击间隔。
- 单次伤害。
- 子弹速度。
- 子弹生命周期。
- 子弹碰撞半径。

玩家按住攻击键后，根据服务器认可的攻击输入和武器冷却时间生成子弹。

服务器负责：

- 验证攻击是否合法。
- 验证攻击冷却时间。
- 生成权威子弹。
- 计算子弹移动。
- 处理碰撞。
- 计算伤害。

客户端负责：

- 播放枪口特效。
- 播放射击音效。
- 展示子弹。
- 播放命中特效。

客户端不能直接决定伤害和击杀结果。

### 3.6 怪物系统

MVP 实现两种普通怪物和一种 Boss。

**近战怪物**

- 寻找附近的存活玩家。
- 主动追击目标。
- 进入攻击范围后进行近战攻击。
- 具有攻击冷却时间。

**远程怪物**

- 选择目标玩家。
- 尝试保持一定距离。
- 向玩家发射远程攻击。
- 具有攻击间隔。

**Boss**

- 具有较高生命值。
- 拥有至少两种攻击方式。
- 根据一定的行为规则切换攻击状态。
- 被击败后结束本次地牢探索。

所有怪物 AI 和战斗判定均由 Go 服务端负责。

客户端仅展示怪物状态和对应动画。

### 3.7 道具系统

MVP 实现基础生命恢复道具。

道具具有：

- 唯一 ID。
- 道具类型。
- 世界位置。
- 道具状态。
- 道具效果。

玩家接触道具后，可以向服务端提交拾取请求。

服务端负责验证距离、道具状态和拾取合法性，并更新玩家生命值及道具状态。

后续可扩展金币、武器和其他增益道具。

### 3.8 游戏结算系统

每局游戏结束后，由服务器统一计算结果。

统计内容：

- 游戏结果。
- 通关时间。
- 玩家击杀数量。
- 玩家受到的伤害。
- 玩家造成的伤害。
- 最终存活状态。

游戏结果包括：

- Victory：成功通关。
- Defeat：队伍失败。

结算数据写入数据库，玩家可以查询历史战绩。

## 4. 游戏实体设计

### 4.1 实体分类

游戏世界中的主要实体包括：

| 实体 | 主要属性 | 主要行为 |
| --- | --- | --- |
| Player | ID、位置、速度、生命值、状态 | 移动、攻击、受伤 |
| Enemy | ID、类型、位置、生命值、AI 状态 | 追击、攻击、死亡 |
| Boss | ID、位置、生命值、阶段 | 特殊攻击、阶段切换 |
| Projectile | ID、位置、速度、伤害、生命周期 | 移动、碰撞、销毁 |
| Pickup | ID、类型、位置、状态 | 生成、拾取、销毁 |
| Door | ID、位置、状态 | 锁定、解锁、切换 |
| Room | ID、地图、敌人列表、房间状态 | 激活、清理、切换 |

### 4.2 实体 ID

所有需要跨网络同步的动态实体必须具有唯一标识。

实体 ID 由服务端生成，客户端不得自行决定权威实体 ID。

实体创建和销毁需要通过网络消息通知相关客户端。

### 4.3 实体同步原则

不同实体采用不同的同步策略。

| 实体 | 同步方式 |
| --- | --- |
| 本地玩家 | 客户端预测 + 服务端校正 |
| 远端玩家 | 服务端快照 + 插值 |
| 普通怪物 | 服务端快照 + 插值 |
| Boss | 服务端快照 + 插值 |
| 子弹 | 服务端权威生成与模拟 |
| 道具 | 可靠生成事件 + 状态同步 |
| 门与出口 | 可靠事件同步 |

## 5. 核心游戏规则

### 5.1 移动规则

玩家通过二维方向输入控制角色移动。

服务器根据输入方向、移动速度和固定模拟时间计算角色位置。

角色不能穿过地图墙体或其他禁止通行区域。

玩家移动速度由服务器配置，客户端不能直接修改权威移动速度。

### 5.2 攻击规则

玩家可以向任意方向瞄准并攻击。

攻击必须满足：

1. 玩家处于存活状态。
2. 当前武器允许攻击。
3. 攻击冷却时间已经结束。
4. 攻击输入通过服务端验证。

服务器生成子弹并计算实际碰撞结果。

### 5.3 碰撞规则

MVP 使用简化的二维碰撞模型。

碰撞对象包括：

- 玩家与墙体。
- 怪物与墙体。
- 子弹与墙体。
- 子弹与敌对单位。
- 玩家与道具。

服务端使用独立的二维碰撞逻辑，不直接依赖 Unity 物理引擎。

### 5.4 伤害规则

伤害由服务端统一计算。

攻击命中后：

- 更新目标生命值。
- 判断是否死亡。
- 触发对应死亡事件。
- 必要时生成掉落物。

客户端不能直接提交最终伤害值或目标死亡状态。

### 5.5 房间推进规则

当前房间的全部敌人被击败后：

1. 服务端判断房间是否清理完成。
2. 房间状态变为 Cleared。
3. 出口由 Locked 变为 Open。
4. 玩家进入出口区域。
5. 服务端检查所有存活玩家是否到达出口。
6. 满足条件后开始房间切换。
7. 服务端加载下一房间并同步初始状态。

## 6. 房间生命周期设计

需要区分两个概念：

**游戏房间（Game Session）**：玩家组队和进行一局游戏的整体会话。

**地牢房间（Dungeon Room）**：游戏会话内部的单个战斗地图。

### 6.1 游戏会话生命周期

游戏会话包含以下状态：

| 状态 | 说明 |
| --- | --- |
| Waiting | 等待玩家加入 |
| Preparing | 玩家准备阶段 |
| Running | 游戏进行中 |
| Victory | 成功通关 |
| Defeat | 队伍失败 |
| Closed | 会话关闭 |

状态转换：

Waiting → Preparing → Running → Victory / Defeat → Closed

### 6.2 地牢房间生命周期

单个地牢房间包含以下状态：

| 状态 | 说明 |
| --- | --- |
| Loading | 加载房间数据 |
| Active | 房间战斗进行中 |
| Cleared | 房间内敌人已全部消灭 |
| Transitioning | 正在切换到下一房间 |
| Finished | 本局最后一个房间已完成 |

状态转换：

Loading → Active → Cleared → Transitioning → Loading

最后一个 Boss 房间：

Loading → Active → Finished

### 6.3 房间切换

房间切换由服务端控制。

切换过程中：

- 暂停当前房间的战斗模拟。
- 记录玩家当前状态。
- 加载下一个房间。
- 清理上一房间的临时实体。
- 将玩家放置在新房间的出生点。
- 生成新房间敌人。
- 广播房间切换事件。
- 恢复游戏模拟。

房间切换不能由客户端单方面决定。

## 7. 网络与实时同步需求

### 7.1 服务端权威架构

Go 服务端拥有游戏世界的最终状态。

客户端只负责提交输入，不直接提交最终游戏结果。

### 7.2 固定 Tick 模拟

服务端使用固定时间步长推进游戏世界。

初始设计参数：

| 参数 | 初始值 |
| --- | ---: |
| 服务端模拟频率 | 30 Hz |
| 客户端渲染频率 | 60 FPS |
| 客户端输入发送频率 | 30 Hz |
| 世界快照发送频率 | 10～15 Hz |
| 最大玩家人数 | 4 |

以上参数属于初始实验配置，后续根据测试结果调整。

### 7.3 客户端预测

本地玩家移动不等待服务端响应。

客户端立即根据输入执行预测，并保存尚未被服务端确认的输入。

收到服务端状态后：

1. 对比服务器确认状态。
2. 恢复服务器权威位置。
3. 删除已确认输入。
4. 重新执行尚未确认的输入。
5. 更新本地预测位置。

### 7.4 远端实体插值

远端玩家和怪物采用状态快照插值。

客户端缓存历史快照，根据服务器 Tick 或时间戳，在相邻快照之间计算实体位置。

### 7.5 网络异常处理

系统应具备：

- 心跳检测。
- 重复消息处理。
- 过期消息过滤。
- 断线检测。
- 网络延迟统计。
- 丢包测试能力。

断线重连可以作为后续扩展功能，MVP 首先保证正常连接和断线后的会话清理。

## 8. 非功能需求

### 8.1 性能需求

在目标测试环境下：

- 游戏客户端目标帧率为 60 FPS。
- 服务端能够稳定维持 30 Hz 模拟。
- 单个房间支持最多 4 名玩家。
- 网络状态波动时，不应出现持续性的实体位置异常。

具体性能指标通过后续测试确定。

### 8.2 可维护性

客户端、服务端和协议定义应相互独立。

游戏玩法逻辑不应直接依赖底层网络实现。

更换传输层时，不应大规模修改游戏业务代码。

### 8.3 可测试性

系统应提供网络测试能力，能够模拟不同网络环境。

建议测试：

- 50ms 延迟。
- 100ms 延迟。
- 200ms 延迟。
- 1% 丢包率。
- 3% 丢包率。
- 5% 丢包率。

重点观察玩家位置误差、状态校正次数、快照接收情况和客户端表现。

## 9. MVP 范围

### 9.1 MVP 必须实现的内容

**游戏内容**

- 2～4 人合作游戏。
- 一种可操作角色。
- 一种基础远程武器。
- 两种普通怪物。
- 一种 Boss。
- 一个完整地牢流程。
- 两个普通房间和一个 Boss 房间。
- 基础生命值与伤害系统。
- 基础生命恢复道具。
- 游戏胜负结算。

**业务系统**

- 用户登录。
- 房间创建和加入。
- 玩家准备与开始游戏。
- 房间生命周期管理。
- 游戏记录持久化。
- 历史战绩查询。

**网络系统**

- Unity 与 Go 跨语言通信。
- Protobuf 消息序列化。
- KCP 通信。
- 服务端固定 Tick。
- 服务端权威移动。
- 客户端预测与状态校正。
- 远端玩家和怪物插值。
- 服务端权威战斗判定。
- 基础延迟和丢包测试。

### 9.2 后续扩展内容

以下内容不纳入第一版 MVP：

- 随机地牢生成。
- 多种可选角色。
- 多武器和复杂武器词条。
- 复杂装备与局外养成。
- 队友复活。
- 复杂技能系统。
- 好友与聊天系统。
- 跨服匹配。
- 断线重连与战局恢复。
- 完整 Rollback Netcode。
- 复杂反作弊系统。

这些功能可以根据剩余时间选择性实现。

## 10. MVP 验收标准

项目至少需要满足以下验收条件：

1. 两个独立 Unity 客户端能够连接同一个 Go 游戏服务器。
2. 两名玩家能够进入同一游戏房间。
3. 两名玩家能够在同一地牢房间中实时移动。
4. 本地玩家移动具备客户端预测和服务端状态校正。
5. 远端玩家和怪物能够平滑显示。
6. 玩家能够攻击怪物，服务端能够正确计算碰撞和伤害。
7. 怪物 AI 能够独立运行并攻击玩家。
8. 击败全部怪物后，房间出口正确解锁。
9. 玩家能够进入下一房间。
10. 玩家能够完成 Boss 战并触发胜利结算。
11. 所有玩家被击败时，能够触发失败结算。
12. 游戏结果能够保存并查询。
13. 在模拟网络延迟和丢包的环境下，系统仍能保持基本可玩性。
14. 能够通过实验数据对客户端预测和插值的效果进行分析。

## 11. 项目开发原则

本项目采用渐进式开发方式。

优先验证底层通信和权威模拟，再逐步扩展游戏玩法。

开发顺序：

1. Unity 与 Go 的 Protobuf/KCP 跨语言通信验证。
2. 单房间、双客户端实时移动。
3. Go 服务端固定 Tick 和权威模拟。
4. 客户端预测、状态校正和插值。
5. 怪物 AI、子弹、碰撞和战斗系统。
6. 房间管理和地牢推进。
7. Boss、结算和数据持久化。
8. 网络测试与性能分析。

开发过程中，必须优先保证核心流程完整，不以增加游戏内容数量为主要目标。

**项目最终交付目标：一个能够由 2～4 名玩家共同完成地牢探索的在线合作游戏，以及一套具备服务端权威模拟和客户端预测能力的实时网络架构。**
